# Деградация сервисов

Дашборд по случаям деградации сервисов. PostgreSQL 18, FastAPI, React + Vite (SCSS), вход через Keycloak, всё крутится в Docker.

## Запуск

Пароли и публичный адрес берутся из `.env`, без него compose не стартует. Для локального запуска хватит шаблона:

```sh
cp .env.example .env
docker compose up -d --build
```

Keycloak стартует секунд 20–30, фронт ждёт его готовности.

- дашборд: http://localhost:8000 (вход — `reader` / `reader` или `editor` / `editor`, пароли из `.env`)
- Swagger: http://localhost:8000/api/docs
- админка Keycloak: http://localhost:8000/auth/admin/ (логин и пароль — `KC_ADMIN_*` из `.env`)
- Adminer: http://localhost:8080 (сервер `db`, логин `postgres_admin`, пароль — `POSTGRES_PASSWORD` из `.env`, база `testdb`)
- Postgres: localhost:5432

Если порты заняты, их можно переопределить:

```sh
DB_HOST_PORT=55432 ADMINER_HOST_PORT=8081 WEB_HOST_PORT=8001 docker compose up -d
```

От адреса дашборда зависят вход и проверка токенов. При смене `WEB_HOST_PORT` адрес пересчитается сам, а если дашборд открывают не с `localhost`, пропишите `PUBLIC_URL` в `.env`.

Код копируется в образ при сборке, поэтому после правок нужно пересобрать сервис:

```sh
docker compose up -d --build backend
docker compose up -d --build frontend
```

Фронт удобнее править через dev-сервер Vite (нужен Node 22+):

```sh
cd frontend
npm install
npm run dev
```

Он поднимется на http://localhost:5173 и будет проксировать `/api` и `/auth` в запущенные контейнеры.

## Как устроено

```
браузер -> frontend (nginx, :8000) -> статика React
                                   -> /api/*  -> backend (FastAPI) -> db (PostgreSQL)
                                   -> /auth/* -> keycloak
```

Фронт собирается внутри образа (`npm run build`), nginx отдаёт статику и проксирует `/api/*` на бэкенд, а `/auth/*` в Keycloak. Страница, API и Keycloak живут на одном адресе, поэтому CORS не нужен и тихая проверка входа в iframe не упирается в блокировку сторонних cookie.

Эндпоинты бэкенда:

```
GET  /api/data?from=2026-01-01&to=2026-03-31     reader, editor
POST /api/cases                                  editor
POST /api/cases/import[?dry_run=true]            editor
```

`GET /api/data` отдаёт все данные для дашборда за период. Без `from`/`to` берётся последний месяц, за который есть данные.

`POST /api/cases` записывает новый случай деградации. Это демонстрационная запись для проверки ролей, в интерфейсе её нет. Операция и продукт определяются сервисом:

```json
{"service_id": 1, "metric_id": 1, "bucket_id": 3, "case_date": "2026-10-14"}
```

Сервис должен быть действующим, дата — не в будущем и не раньше 2000 года. Лишние поля и строки вместо чисел не принимаются. В ответ приходит `201` и созданная запись с `id`, `created_at` и `created_by` (имя пользователя из токена).

`POST /api/cases/import` импортирует случаи из CSV, это его вызывает кнопка «Импорт» (см. ниже). Тело запроса — текст файла (`Content-Type: text/csv`). С `?dry_run=true` сервер только проверяет файл и отвечает, сколько записей добавится в какие сервисы и месяцы и какие строки с ошибками. Без него проверяет ещё раз и записывает все строки одной транзакцией: `201 {"added": 519}`. Если хоть одна строка с ошибкой, не записывается ничего. Правила для строк те же, что у `POST /api/cases`.

Ошибки приходят в виде `{"error": "..."}`: 400 на неправильные даты или данные, 401 без токена или с плохим токеном, 403 если не хватает роли, 404 если случаев нет или такого роута нет, 409 если сервис убрали в архив прямо во время импорта, 413 если файл больше 1 МБ, 422 если тело запроса не по форме, 500 при ошибке БД.

## Вход и права

Используется OpenID Connect, Authorization Code Flow с PKCE (S256). Клиент `dashboard` в realm `degradations` публичный, без секрета. Вход по логину и паролю напрямую (password grant) выключен.

1. Страница при открытии тихо спрашивает Keycloak, есть ли вход (`frontend/src/auth.js`, библиотека `keycloak-js`). Если нет, показывает экран «Войти».
2. «Войти» ведёт на страницу Keycloak, после входа браузер возвращается на дашборд с кодом, и `keycloak-js` меняет его на токены.
3. Каждый запрос к API несёт `Authorization: Bearer <access token>`. Перед запросом токен обновляется, если ему осталось меньше 30 секунд (живёт он 5 минут).
4. Бэкенд (`backend/app/auth.py`) проверяет подпись RS256 по ключам Keycloak, `iss`, `aud` = `dashboard-api` и срок. Роли он берёт из `realm_access.roles`.

Роли и тестовые пользователи заданы в `keycloak/realm-degradations.json`:

| Пользователь | Роль | Может |
|---|---|---|
| `reader` | `reader` | смотреть дашборд, выгружать Excel |
| `editor` | `editor` | то же плюс запись: импорт CSV кнопкой «Импорт» и `POST /api/cases` |

Пароли тестовых пользователей подставляются при импорте из `KC_READER_PASSWORD` и `KC_EDITOR_PASSWORD`. Без роли пользователь войдёт, но API ответит 403: на странице будет текст ошибки и кнопка выхода.

У reader кнопка «Импорт» серая и не нажимается, при наведении подсказка объясняет, что не хватает прав. Это только для удобства, права проверяет бэкенд: запрос reader на запись получит 403.

Keycloak запущен в режиме `start-dev` со встроенной базой. Realm импортируется из `keycloak/realm-degradations.json` при создании контейнера, поэтому правки в админке живут до пересоздания контейнера (`down` или `up` после изменения compose). Чтобы правка сохранилась, вносите её в `realm-degradations.json`.

Страница входа Keycloak оформлена под дашборд: тема `degradations` в `keycloak/themes/degradations/login` наследует разметку классической темы `keycloak`, а все стили свои (`resources/css/degradations.css`). Шрифт берётся из `/fonts/` фронта, Keycloak открыт на том же адресе. В `start-dev` темы не кэшируются, так что правка CSS видна после обновления страницы. Язык у realm один, русский, поэтому переключателя языка на странице нет.

Для прода это не годится как есть:

- Keycloak нужен в режиме `start` с внешней базой (тем же Postgres) и HTTPS;
- пароли — свои, через секреты окружения, тестовых пользователей убрать;
- `/auth/admin/` не стоит отдавать наружу через тот же nginx.

## Данные

Источник истины — PostgreSQL. CSV нужны только для первого наполнения пустой базы.

Схема и загрузка CSV — один файл `db/init.sql`, сами данные — CSV в `db/seed/`. Postgres выполняет `init.sql` сам и ровно один раз: при первом старте с пустым томом, в одной транзакции. Рестарты и пересборки его не выполняют, правки CSV в существующую базу не попадают. Залить CSV заново можно только с пересозданием базы (сотрёт всё, что добавили через API):

```sh
docker compose down -v && docker compose up -d
```

Отсюда же ограничение: изменение `init.sql` подхватит только новая база. В уже работающую базу правку схемы нужно внести отдельным SQL (`ALTER TABLE …`) или пересоздать базу.

**Модель.** Иерархия: продукт → операция → сервис. Главная сущность при вводе — сервис. Запись о деградации (`degradation_case`) ссылается только на `service_id`, а операция и продукт определяются сервисом. Каждый случай хранит дату (`case_date`), метрику и диапазон (`bucket_id`). Точный процент не храним, только диапазон с шагом 10%: 0–10, 11–20, …, 91–100 (таблица `bucket`). По этим же диапазонам строятся колонки в таблице на дашборде.

Сервисы, операции и продукты — справочники в базе, в коде фронта и бэка их названий нет. Новый сервис — это строка в `service`. Он сразу появляется на дашборде, и на него можно создавать записи:

```sql
INSERT INTO service (operation_id, name, created_by) VALUES (2, 'Проверка лимитов', 'admin');
```

Сервис с записями удалить нельзя, не даст внешний ключ. Вместо этого его убирают в архив (`is_active = false`): новую запись на архивный сервис API не примет, но его история остаётся на дашборде.

Под будущие POST / PATCH / DELETE:

- id продуктов, операций и сервисов выдаёт база (identity);
- у продуктов, операций, сервисов и записей есть `created_at`, `created_by`, `updated_at`, `updated_by`. `created_by` обязателен, его пишет API (у строк из seed — `seed`). `updated_at` ставит триггер при любом UPDATE, `updated_by` — API;
- названия не пустые и не повторяются внутри своей группы (продукт, операция продукта, сервис операции);
- индексы по дате и сервису у записей.

Демо-данные ненастоящие и покрывают период с сентября 2025 по октябрь 2026. Октябрь 2026 взят из `пример.xlsx`: количество случаев по диапазонам совпадает, даты раскиданы с 1 по 10 октября. Остальные месяцы сгенерированы по его образцу. Для старта с реальными данными замените `db/seed/degradation_case.csv` (и справочники, если нужно) до первого запуска или перед `down -v`.

## Степени деградации

Диапазоны группируются в четыре степени (названия взяты из МУ):

| Степень | По умолчанию |
|---|---|
| минимальная | 0–20% |
| частичная | 21–50% |
| значительная | 51–80% |
| полная | 81–100% |

Дефолтные границы задаются в `STEPEN_BOUNDS` (`frontend/src/config.js`).

Для отдельного сервиса границы можно поменять прямо на странице: клик по чипу сервиса в таблице открывает окно со слайдером. Ненужную степень можно выключить, тогда её диапазон забирает соседняя. Сервисы со своими границами обведены чёрным. Эти настройки живут только в стейте (`serviceBounds` в `App.jsx`), на сервер не уходят и пропадают после перезагрузки страницы.

## Период и фильтры

Период выбирается в верхней панели: месяц, год или произвольный диапазон дат. По умолчанию открыт последний месяц, а в режиме диапазона выбраны все данные. Там же фильтр по продукту. Бэкенд всегда получает две даты, месяц и год переводятся в них на фронте (`frontend/src/period.js`).

## Выгрузка в Excel

Кнопка Export справа в панели скачивает `.xlsx` за выбранный период и продукт. В файле два листа:

- «Без изменений» — у всех сервисов границы степеней по умолчанию;
- «С изменениями» — со своими границами сервисов, как сейчас на странице. Если границы меняли, сверху есть таблица с ними.

На каждом листе для обеих метрик («Без учета 5 минут» и «С учетом 5 минут») есть сводка по степеням (как на кольце), список сервисов (как полосы под кольцом) и детализация с той же раскраской, что на странице.

Файл собирается в браузере через [ExcelJS](https://github.com/exceljs/exceljs) (`frontend/src/excel.js`), бэкенд в этом не участвует. Библиотека тяжёлая (~250 КБ в gzip), поэтому грузится только по нажатию кнопки.

## Импорт из CSV

Кнопка «Импорт» слева от Export добавляет случаи деградации из CSV. Она активна только у роли `editor`.

1. В окне перетащите файл на пунктирную панель или нажмите на неё и выберите. Формат как у `db/seed/degradation_case.csv`: колонки `service_id,metric_id,bucket_id,case_date`, дата в виде `ГГГГ-ММ-ДД`. Разделитель `;` тоже подходит, так сохраняет CSV Excel с русской локалью. Файл не больше 1 МБ.
2. Сервер проверяет файл, в базу пока ничего не пишется. Окно показывает, сколько записей добавится, и таблицу «сервис × месяц». Строки с ошибками выводятся с номерами и причинами, такой файл принять нельзя.
3. «Принять изменения» записывает все строки одной транзакцией от имени того, кто вошёл (`created_by`), и дашборд обновляется.

Повторы не отсеиваются: один и тот же файл, импортированный дважды, добавит записи дважды. Одинаковые случаи в один день — нормальные данные, отличить повтор от настоящего случая нельзя.

## Структура

```
compose.yaml            db, adminer, keycloak, backend, frontend
.env.example            шаблон .env: пароли и публичный адрес
docker/db/Dockerfile    Postgres с русской локалью (ICU)
db/
  init.sql              схема и загрузка CSV — один раз, на пустой базе
  seed/                 CSV для первого наполнения
keycloak/
  realm-degradations.json  realm: клиент dashboard, роли reader/editor, тестовые пользователи
  themes/degradations/     тема страницы входа в стиле дашборда

backend/
  app/main.py           роуты /api/data, /api/cases и /api/cases/import, ошибки
  app/auth.py           проверка токена Keycloak и ролей (401/403)
  app/cases.py          проверка новых случаев и разбор CSV для импорта
  app/data.py           запросы к БД и сборка ответа
  app/db.py             подключение к БД

frontend/
  Dockerfile, nginx.conf
  public/               шрифты, иконка, silent-check-sso.html для тихой проверки входа
  src/main.jsx          точка входа: проверка входа, App или экран входа
  src/App.jsx           вся страница: стейт и загрузка данных
  src/components/       компоненты, у каждого своя папка (Donut/Donut.jsx + Donut.scss)
  src/*.js              логика без React: calc, bounds, period, auth, api, helpers, config, excel
  src/styles/           global.scss (шрифты, цвета, базовые стили), dialog.scss (оболочка окон) и _mixins.scss
```
